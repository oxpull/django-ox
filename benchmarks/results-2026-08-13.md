# Benchmark results, 2026-08-13

django-ox 0.1.0 vs django-tasks-db 0.12.0 on identical no-op workloads.
Methodology, exact commands, and limitations are in [README.md](README.md).
Raw data, including all 500 individual latency samples per run, is in
[results-raw-2026-08-13.json](results-raw-2026-08-13.json); that file is the
source of truth and this document is written from it. All runs are reported.
No runs were discarded.

## Environment

- Apple M1 Max, 10 logical cores (8 performance, 2 efficiency), 64 GiB RAM
- macOS 26.5.2
- Python 3.12.13, Django 6.0.8, psycopg 3.3.4 (binary)
- django-ox 0.1.0 (editable install from this repo), django-tasks-db 0.12.0
  with django-tasks 0.12.0 (PyPI)
- PostgreSQL 16.14 (Debian, official postgres:16 image) in Docker Desktop on
  the same machine, port-forwarded to localhost:54330
- Both backends at defaults except: `DEBUG = False`, console logging capped
  at WARNING, and `--no-startup-delay` on db_worker (see README)

## Enqueue throughput

2,000 sequential `enqueue()` calls, single producer, autocommit. Higher is
better.

| Run | django-ox (tasks/sec) | django-tasks-db (tasks/sec) |
| --- | --- | --- |
| 1 | 1040.4 | 471.1 |
| 2 | 634.6 | 490.9 |
| 3 | 619.3 | 425.9 |

Wall time for the 2,000 calls: ox 1.92 s / 3.15 s / 3.23 s, tasks-db
4.25 s / 4.07 s / 4.70 s.

ox's run 1 (1040/s) is an outlier against its own runs 2 and 3; it was the
first measurement taken after the container was created and we did not
identify the cause. Treating ox as roughly 620 to 640 tasks/sec steady
state is the conservative reading. It is faster than django-tasks-db on this
metric in all three runs regardless.

## Findings

ox is faster at getting tasks into the queue and much slower at getting
them out. On the producer side it enqueued 2,000 tasks in 1.9 to 3.2 seconds
against django-tasks-db's 4.1 to 4.7 seconds, and in-transaction enqueue
latency is a tie at roughly half a millisecond p50 for both. On the worker
side ox lost every cell. At concurrency 4 it completed 2,000 no-op tasks
in 8.1 to 9.4 seconds against 5.4 to 5.5 seconds for four db_worker
processes. At concurrency 1 with default settings it did not finish inside
the 900 second timeout in any run, sustaining 0.86 tasks per second against
django-tasks-db's 70.

The concurrency-1 failure has a specific mechanism. ox's worker main loop
claims a task, hands it to the executor, and then, finding its single
executor slot occupied, sleeps for the full idle poll interval (default 1.0
s) before checking again. For tasks shorter than the interval, throughput is
capped near one task per interval. The arithmetic is consistent across
configurations: per-task cycle time was 1.163 s at the default interval and
0.263 s at interval 0.1, in both cases the interval plus a stable residual
of 0.163 s. A single further probe at interval 0.01 measured 100 ms per
task, not the 173 ms the constant-residual model predicts, so the residual
is not a fixed per-cycle cost and we do not have a verified explanation for
it; it needs profiling, not guessing. What the probes do establish is that
even at the most aggressive non-default interval ox's single-slot loop
sustained under 10 tasks per second on this workload, where db_worker's
defaults sustained 70.

Two honest caveats in django-tasks-db's favor and one in ox's. First, its
concurrency-4 configuration used four processes (its only scaling model),
which is not identical work to ox's four threads in one process; four
interpreters avoid the GIL but cost four Django boots, and the numbers
include both effects. Second, db_worker at default verbosity writes two log
lines per task to its log file, an included cost that ox (silent at
WARNING) did not pay; at its measured 14 ms per task this is noise. Third,
ox's enqueue throughput win is real but small in absolute terms, and its
run 1 outlier (1040 tasks/sec) remains unexplained; do not quote it.

The actionable conclusion for ox: the worker loop must re-check for free
slots when a task completes instead of sleeping the full poll interval, and
the 0.163 s per-cycle residual at concurrency 1 needs profiling. Until the
loop is fixed, ox's honest positioning against django-tasks-db is stronger
transactional enqueue semantics, not worker throughput, because on worker
throughput it currently loses.

## Post-fix addendum (added by root session, 2026-08-13 02:57, from date)

The concurrency-1 DNF above was diagnosed as a worker main-loop bug: when every executor slot
was busy, the loop slept the full poll interval (1.0 s default) instead of waking when a task
finished. Fixed in worker.py (futures-aware wait, FIRST_COMPLETED) immediately after the matrix
completed; full test suite stayed green (51 passed). The matrix was then re-run once (--runs 1,
same harness, same container recipe; pre-fix raw data preserved in
results-raw-2026-08-13-prefix.json).

Post-fix, single run (label: 1 run, not 3 — treat as indicative):

| Cell | django-ox | django-tasks-db |
| --- | --- | --- |
| Enqueue throughput | 584 tasks/sec | 539 tasks/sec |
| Enqueue latency p50/p95 | 0.58 / 0.69 ms | 0.56 / 0.65 ms |
| End-to-end c1 | 37.1 s (54 tasks/sec) | 28.2 s (71 tasks/sec) |
| End-to-end c4 | 8.3 s (242 tasks/sec) | 5.4 s (372 tasks/sec) |
| Diagnostic c1 --interval 0.1 | 37.0 s (54 tasks/sec) | n/a |

The diagnostic now matches the default-interval cell, confirming the poll interval no longer
bounds throughput. Remaining honest gap: ~18.5 ms/task per-task cost at c1 vs ~14.1 ms/task for
django-tasks-db, and the c4 comparison is 4 threads (GIL-shared) vs 4 processes. The no-op
throughput gap is real and unflattering; it is also not the product's claim (transactional
enqueue and durability are). Per-task query count is the suspected cost and is a pre-release
optimization item.

## Increment 4 addendum (added 2026-08-13 03:07, from date) — claim-path optimization

Numbers above this line are pre-increment-4 and are preserved unchanged.

The suspected per-task query cost was confirmed by profiling (see
BUILD-NOTES.md, Increment 4): ox's worker executed 8 SQL statements per
task in the threaded c1 path, at ~2.2 ms of round-trip overhead each on this
localhost-Docker setup. The claim path was reduced to a single
`UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING *`
statement on PostgreSQL, per-attempt bookkeeping was folded into the claim
UPDATE, and the two per-task re-fetches were removed: 8 statements per task
became 2. Test suite after the change: 54 passed on SQLite, 54 passed on
PostgreSQL 16 (three consecutive runs).

Post-optimization e2e, same harness (`run_e2e`), same container, **1 run
per cell** (indicative, not a 3-run matrix; raw JSON in
results-raw-2026-08-13-inc4.json):

| Cell | django-ox | django-tasks-db |
| --- | --- | --- |
| End-to-end c1 | 22.6 s (88.5 tasks/sec) | 28.0 s (71.4 tasks/sec) |
| End-to-end c4 | 5.0 s (398.2 tasks/sec) | 5.4 s (373.1 tasks/sec) |

Against the post-fix addendum above: ox c1 went from 37.1 s (54/s) to
22.6 s (89/s) and c4 from 8.3 s (242/s) to 5.0 s (398/s); tasksdb's numbers
in this session (28.0 s / 5.4 s) match its earlier runs. ox now leads both
cells. Caveats: one run per cell, and the c4 thread-vs-process asymmetry
described in the README still applies (it now runs against ox, which wins
the cell while sharing one interpreter). Enqueue-side metrics were not
re-run; nothing in this change touches the enqueue path. Re-run the full
3-run interleaved matrix before publishing any of these numbers.
