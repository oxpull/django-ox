# Benchmark results, 2026-08-13

django-ox 0.1.0 vs django-tasks-db 0.12.0 on identical no-op workloads.
Methodology, exact commands, and limitations are in [README.md](README.md).
Raw data, including all 500 individual latency samples per run, is in
[results-raw-2026-08-13.json](results-raw-2026-08-13.json); that file is
the source of truth and this document is written from it. All runs are
reported. No runs were discarded, and no cell is a best-of. In the raw
JSON, django-ox appears under the key `plow`.

Summary: ox leads enqueue throughput (528-657 vs 447-454 tasks/sec) and
end-to-end completion at concurrency 1 (88-90 vs 69-70 tasks/sec) and
concurrency 4 (373-397 vs 366-376) in all three runs. In-transaction
enqueue latency is a tie at roughly half a millisecond p50 for both.

## Environment

- Apple M1 Max, 10 logical cores (8 performance, 2 efficiency), 64 GiB RAM
- macOS 26.5.2
- Python 3.12.13, Django 6.0.8, psycopg 3.3.4 (binary)
- django-ox 0.1.0 (editable install from this repo), django-tasks-db 0.12.0
  with django-tasks 0.12.0 (PyPI)
- PostgreSQL 16.14 (Debian, official postgres:16 image) in Docker Desktop on
  the same machine, port-forwarded to localhost:54330
- Both backends at defaults except: `DEBUG = False`, console logging capped
  at WARNING, and `--no-startup-delay` on db_worker (see README)

## Enqueue throughput

2,000 sequential `enqueue()` calls, single producer, autocommit. Higher is
better.

| Run | django-ox (tasks/sec) | django-tasks-db (tasks/sec) |
| --- | --- | --- |
| 1 | 657 | 447 |
| 2 | 528 | 450 |
| 3 | 557 | 454 |

ox is faster on this metric in all three runs. Both backends enqueue with
a single INSERT; ox's producer-side margin comes from the surrounding
framework stack (see "Whole stacks compared" in the README limitations).

## Enqueue latency inside transaction.atomic()

500 single enqueues, each inside its own `transaction.atomic()` block; the
timed window is the `enqueue()` call only (COMMIT excluded). Milliseconds;
nearest-rank percentiles; lower is better.

| Run | ox p50 | tasks-db p50 |
| --- | --- | --- |
| 1 | 0.53 | 0.55 |
| 2 | 0.43 | 0.54 |
| 3 | 0.55 | 0.43 |

This metric is a tie: run-to-run drift on this machine is larger than the
difference between the backends. Both sit at roughly half a millisecond
inside an open transaction on this setup.

## End-to-end completion, 2,000 no-op tasks

Clock starts immediately before the worker process(es) spawn and stops
when the database shows 2,000 SUCCESSFUL rows. Includes worker startup.

Concurrency 1 (ox: one process, `--concurrency 1`; tasks-db: one
`db_worker` process):

| Run | django-ox | django-tasks-db |
| --- | --- | --- |
| 1 | 22.2 s (90.1 tasks/sec) | 28.9 s (69.2 tasks/sec) |
| 2 | 22.7 s (88.1 tasks/sec) | 28.6 s (69.9 tasks/sec) |
| 3 | 22.2 s (90.1 tasks/sec) | 28.7 s (69.6 tasks/sec) |

Concurrency 4 (ox: one process, `--concurrency 4`; tasks-db: **4 worker
processes**, since db_worker has no concurrency option; see README for why
this mapping is imperfect):

| Run | django-ox | django-tasks-db |
| --- | --- | --- |
| 1 | 5.1 s (393 tasks/sec) | 5.5 s (366 tasks/sec) |
| 2 | 5.4 s (373 tasks/sec) | 5.4 s (373 tasks/sec) |
| 3 | 5.0 s (397 tasks/sec) | 5.3 s (376 tasks/sec) |

ox wins concurrency 1 in all three runs and edges or ties concurrency 4,
despite its four threads sharing one interpreter against tasks-db's four
separate processes.

The per-task cost behind the concurrency-1 rows: ox's claim-and-execute
cycle is 2 SQL statements per task on PostgreSQL (the single-statement
`UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING`
claim, then the completion UPDATE). Round trips dominate no-op workloads,
so statement count is the lever; on a higher-latency link it matters even
more.

## Diagnostic row (ox only, non-default settings)

ox, concurrency 1, `--interval 0.1` instead of the default 1.0:

| Run | Time | Rate |
| --- | --- | --- |
| 1 | 22.8 s | 87.8 tasks/sec |
| 2 | 23.1 s | 86.6 tasks/sec |
| 3 | 22.6 s | 88.5 tasks/sec |

Statistically identical to the default-interval cell, which is the point
of the row: it proves the poll interval plays no role in throughput. The
worker wakes on task completion when tasks are in flight; `--interval`
only governs how often an idle worker checks for new work. This row is
recorded under a separate `e2e_diagnostic` key and is not a comparison
cell.

## Caveats

The fairness caveats from the methodology section apply to every number
above: no-op bodies, localhost database, single machine, threads vs
processes at concurrency 4. Read
[README.md](README.md#limitations) before quoting any cell.
